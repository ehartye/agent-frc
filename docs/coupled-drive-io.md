# Integrated drivetrain, auxiliary wheel and shared supply

This development slice executes one actual desktop Java controller through two drive PWM outputs plus one auxiliary PWM output, two raw DIO encoders and an analog gyro, coupled to a planar drivetrain and the existing source-backed bare-wheel auxiliary mechanism on ONE supply. It is not a second unrelated motor benchmark. It does not establish credible real-robot performance or engineering acceptance: the chassis is a named, explicit, replaceable hypothesis, not an actual robot or measured assembly.

## Actual binding and command

`python scripts/run-coupled-drive.py --step OFFICIAL_AM3608_STEP --density ASSUMED_KG_PER_M3 --output NEW_DIRECTORY --java-home EXISTING_JDK17 --gradle-home EXISTING_OFFLINE_CACHE`

The runner retains exact native-property bytes, hypothetical chassis configuration, compiled-controller class hash, source/wrapper/dependency hashes, test XML and traces. It recompiles Java offline and requires three actual native-extraction tests, three existing IO regressions and thirteen coupled-drive tests, with no skips/errors/failures. Missing inputs and unsupported model states fail rather than count as evidence. The raw CAD bytes and density caveats are unchanged from [the wheel slice](wheel-code-io.md). The genuine wheel is an auxiliary rotating load, NOT the drive traction wheel or chassis mass.

The configuration declares mass45kg, yaw inertia5kg m2, track width0.6m, traction radius0.0762m, reduction10.71 motor revolutions per wheel revolution, two NEO motors per drive side, supply12V/0.02ohm. These chassis/power values are assumptions, not AM14U6 measurements or CAD-derived mass. Actual multi-material chassis CAD/BOM mass assignments, component placements, CoM and assembly omissions are still unavailable. The adapter bounds its development parameter domain and rejects excessive linear damping stiffness; these numerical limits are not physical feasibility ranges. Changing the configuration changes its consumed byte pin; it cannot acquire source-reviewed status merely by being executed.

## Coupled timing and electrical model

The controller reads real simulated Encoder and AnalogGyro interfaces, never plant state. Raw sensor generation uses an independently defined physical pulse convention and explicit clockwise gyro versus counterclockwise field sign. The controller command domain is forward-only0-3m/s per drive side and auxiliary duty0-1. Reverse or arbitrary braking trajectories are not accepted evidence. Controller output is held for20ms. Both drive sides and the native-wheel auxiliary advance on the same1ms substeps, with comparison at0.5ms. Source temperature, battery internal resistance and ideal motor constants do not evolve.

For each ideal averaged bridge, armature current is `(d*V-E)/R`; its battery current is `d*I`, NOT unweighted motor current. At each substep the common bus is solved algebraically:

`V = (Voc + Rb*sum(d*E/R)) / (1 + Rb*sum(d*d/R))`

Effective motor resistance includes motor count. Drive back-EMF uses signed wheel linear speed times reduction divided by traction radius; the auxiliary uses its own motor speed. The same solved voltage feeds every plant input and RoboRioSim. No per-side ideal12V supply or one-subsystem overwrite exists. Samples label electrical values from the start of the final substep and mechanical/sensor values from its end; this stagger is part of the explicit numerical model.

Negative branch battery power beyond numerical tolerance is unsupported regeneration and throws, rather than being clamped into a successful charging/safety result. In the baseline BRAKE mode, duty zero is modeled as a short-circuited armature: **dynamic braking, not coast**. It may dissipate rotor/chassis kinetic energy as copper loss despite zero bus current. Zero PWM is not instant stopping or a certified safe state. The software undervoltage inhibit is a development policy, not modeled real brownout firmware.

Tests independently check KCL and ideal circuit power identities, aggregate sampled source/battery/copper/back-EMF electrical exchange, simultaneous-load effects, finite inputs, straight symmetry, differential yaw, raw sensor conversion/sign, disable behavior, undervoltage demand inhibition and full straight/turn trajectory timestep sensitivity. The supported straight scenario is2s and turn scenario0.4s. Extending the chosen turn to2s enters unsupported branch regeneration; a regression requires that rejection, rather than masking it as success. No general driving envelope is established. Numeric thresholds are development convergence bounds, not hardware or safety limits.

Important limitation: pinned WPILib NEO empirical torque and speed constants are not exactly reciprocal in SI. Consequently back-EMF exchange `E*I` is NOT silently asserted equal to mechanical shaft power `torque*speed`. The electrical identities/ledger are only circuit bookkeeping, not a global motor/mechanical first-law pass. Preserve source constants rather than inventing a corrected real motor; this discrepancy needs characterization/model refinement before physical claims.

## Source choice and unsupported effects

[Pinned WPILib2026.2.1 DifferentialDrivetrainSim](https://github.com/wpilibsuite/allwpilib/blob/v2026.2.1/wpilibj/src/main/java/edu/wpi/first/wpilibj/simulation/DifferentialDrivetrainSim.java) evolves planar pose and left/right speeds/distances using [LinearSystemId](https://github.com/wpilibsuite/allwpilib/blob/v2026.2.1/wpimath/src/main/java/edu/wpi/first/math/system/plant/LinearSystemId.java). Its gearing implementation is interpreted from equations/motor-shaft speed, not ambiguous ratio prose. The chosen plant assumes ideal no-slip traction. It does not simulate tire friction, contact patches, obstacles, carpet, weight transfer or tipping. [MapleSim's documentation](https://shenzhen-robotics-alliance.github.io/maple-sim/simulation-details/) describes2D contact/skid modeling, but no version-pinned MapleSim dependency has been audited or adopted here; its existence does not fill these gaps.

All five required domains remain blocked for engineering acceptance: ideal physics and shared-voltage coverage are partial; thermal dynamics, calibrated friction/contact and chassis weight-distribution behavior are absent. Mass and yaw inertia do not establish3D CoM/load transfer. Supply polarization, wiring/controller losses, current limiting, real sensor/CAN/firmware behavior, inductance, regeneration and physical calibration are unmodeled. No obstacle route, match score, mechanism effectiveness, team selection or robot operation follows from this run. The existing physics gate is unchanged and this adapter is not registered for acceptance. The next credible step is a configured real chassis mass model or measured plant, source/version-audited contact dynamics and supervised calibration/holdout data, not relaxing these unknowns.

Retained failure XML and before/mutated/restored hashes describe an expected negative development test, not acceptance of the faulty code or complete baseline/changed robot validation.

## Explicit ideal brake versus coast extension

[REV basic configuration documentation](https://docs.revrobotics.com/brushless/spark-max/gs/basic-config), reviewed2026-11-16, establishes configurable neutral behavior and describes brake as shorted motor wires. It does not certify this model's deceleration, loss, switching timing or firmware. The existing configuration remains the BRAKE baseline; the independently pinned test defines an explicit COAST alternative under identical active history. Both neutral modes appear with open-branch masks in the retained `neutral-comparison.csv` and receipt.

An open branch requires exactly zero duty and contributes zero armature current, source current and copper loss in this ideal model. The physical motor-derived drivetrain plant substitutes its stage-local back-EMF inside the dynamics equation to cancel motor torque on each open side. This equivalent input is an algebraic modeling device, not a supplied voltage: it bypasses no real device protection and is never counted as bus demand. Each Runge-Kutta stage uses its own state, a copied input and fixed gearing. An arbitrary identified plant is not supported. Mixed open/active sides can still accelerate together through the chassis; coast does not promise constant velocity on each side independently. A both-open drivetrain continues moving with constant velocities because external losses are absent. The open auxiliary retains angular velocity, explicitly a lossless free rotor assumption.

Whole active-plus-disabled trajectories for both modes are independently compared at1ms versus0.5ms with retained development refinement results. The comparison tests the same active history followed by one second of disabled zero duty. Brake predicts internal electrical dissipation and declining speed; ideal coast retains speed and travels farther. Neither zero bus current nor zero PWM proves no stored energy, a safe stop or position holding. Inherited WPILib current telemetry is deliberately unavailable on the neutral-aware model because it does not represent its open boundary; the ledger uses the explicit shared circuit currents.

[REV locked-rotor documentation](https://docs.revrobotics.com/brushless/neo/locked-rotor-testing) distinguishes phase/winding current from supply current and describes SmartCurrentLimit changing output. No current-limit firmware is implemented here; a battery-current cap would not reproduce that behavior. [PWM interface documentation](https://docs.revrobotics.com/brushless/spark-max/control-interfaces) describes neutral on signal loss, but no timeout value or hardware switching delay is simulated. Regeneration remains unsupported, and the long-turn rejection remains mandatory. These rolling documents are source guidance, not a version-pinned firmware implementation. All required-domain acceptance remains blocked.
