# Conceptual design of one robot for a chosen match role

Conceptual design decides what the robot does in a match and roughly what shape it takes to do it, before any CAD. Write the concept of operations (ConOps). Describe each candidate robot as a **concept bot**: one JSON file with its body, swerve drive, input and output ports and a labelled range for every number. Rehearse the candidates on the field, rank them in a concept study, and hand the student's selection to preliminary design. [Concept-bot format and behaviour](../../docs/concept-bots.md) · [Concept study](../../docs/concept-study.md) · [Exit criteria for the three phases](../../docs/design-phase-detail.md)

This skill designs one robot. Alliance-wide role comparison, choosing which role the team's robot should play, belongs to `frc-season-meta`. For a new game, first extract the [project rules model](../../docs/project-rules-model.md) and build the [Field Lab](../../docs/kickoff-field-lab.md). For an existing design, recover the selected cycle and candidate through [design continuation](../../docs/strategy-first-continuation.md).

## Settle the role before the robot

- **Role first.** State the alliance role, the scored event, the reserve time and the fallback. Walk one identifiable piece through approach, capture, retention, transfer, placement and reset, with the robot's position, time and energy at each step. Mark the operations that can overlap and the shared resources that prevent it.
- **Compare allocations, not suppliers.** Sketch competing ways to divide the functions before choosing purchased mechanisms. Start from a simple baseline. Try removing a transfer, reversing a path, using passive geometry or running functions in parallel. State what each candidate deliberately gives up. Each candidate becomes its own concept bot.
- **Partner-dependent roles.** When a role relies on a partner, [compare the complete alliance service chain](../../docs/alliance-completion.md) on the match clock and change partner availability before selecting an architecture. Revisit a selected role with the [saved role and refinement comparison](../../docs/whole-robot-comparison.md#test-a-refinement-against-the-selected-role).

## Steps

1. **Author a concept bot for each candidate.** Keep the ConOps and the concept files in the project, for example under `kickoff/concepts/`. Start from an invented example in `examples/concept-bots/` and replace every number. Give the body, the drive, each input face and each output, and the storage per piece type.
   - Label every value `required`, `assumed` or `observed` and state its basis.
   - For the drive, start from the default swerve bounds in [Default swerve bounds](../../docs/concept-bots.md#default-swerve-bounds), labelled `assumed`. Replace them once the team picks a module, ratio and current limit.
   - **Propose the mass range.** If the profile's `weightLimits` has a limit named `inspection`, propose 75–95% of it. Explain that it assumes a robot built close to the limit with about 5% held back, and that it says nothing yet about this concept's mechanisms. Ask the student for evidence that narrows or shifts it: known component or kit masses, module and battery counts, or a comparable earlier build. Write the refined range with its basis and relabel it `observed` or `assumed`. Without a limit or an estimate, leave mass unresolved.
   - Done when the file validates and no value has an empty basis.
2. **Check it.** `concept:check` reads the rules model's `rehearsal.robotLimits` and an `entry` on every target a ranged output aims at. If either is missing, add it through the rules register with its `factId` first. [Robot limits and entry regions](../../docs/concept-bots.md#robot-limits-and-entry-regions-in-the-rules-model) Then run `npm run concept:check -- concept.json --profile rules-model.json` in the plugin checkout, or `node <plugin-root>/scripts/concept-check.mjs concept.json --profile rules-model.json` from the project. Read each limit as `within`, `exceeds` or `unresolved`, the mass share of the limit, and each ranged output's stand-off band per target. Treat `exceeds` as a design finding, not an error. Done when every `unresolved` is either resolved or recorded as an open question.
3. **Rehearse it.** Build the lab with `--concept` for each file and choose the concept on a robot card. Play the same scoring opportunity with each candidate and the same partners and opponents. To compare two concepts by hand, run a matched [match series](../../docs/match-series.md) that changes only the focal robot's concept. Compare when pieces are acquired, the turns, the waits, the aim and slew time and the expected points. Read every notice in the narrative download, such as an ignored step rate, an unknown piece radius or no arc from a pose. The rehearsal has no drag, mass never changes speed, and accuracy does not vary with range: say so beside any result that depends on them. Done when the narrative is saved with the concept ID and digest.
4. **Rank the candidates in a concept study.** Write an `agent-frc/alliance-study@1` study with an `id`, the rules profile pinned as `profile: {file, sha256}`, one role per candidate pinned as `concept: {file, sha256}`, and at least three contexts that change what the focal robot faces. Put enough loose pieces on the field that the candidates still have work in the last period. Leave the default sweeps on, and add an explicit axis where the team knows a better range. Sweeps change single numbers only: turret travel and slew, elevation, launch speed and every other `{min, max}` range are never swept, so to test one, author a variant concept by hand and add it as another role. Run `node <plugin-root>/scripts/concept-tournament.mjs study.json --out results.json --html results.html` from the project (`npm run concept:study --` in the plugin checkout). Exit 3 means the run budget stopped it: turn the defaults off and sweep the quantities that matter with explicit axes, narrow the contexts, or pass `--allow-long` after telling the student how long it will take. A sweep that changes nothing is a finding: say why, for example pieces too close together for top speed to matter. Read the ranking, the cost signals and Pareto flag, any robot-limit warning, the fragility banner and each competitive range with its break-evens. Each range holds the other quantities at base. Done when the results file and page are saved and the student has seen which assumptions the leader depends on.
5. **Let the student select.** The ranking is a recommendation, not a decision: present it with its fragility and leave the choice to the student, who may pick a candidate that is not first. Run `node <plugin-root>/scripts/concept-select.mjs results.json --candidate ID --basis "the student's reason" --out kickoff/selection` from the project root. Use `--interface PART=GROUP` when the preliminary design's group names are known, including `--interface robot=<group>` for the mass premise. Each rate premise bounds only the quantity's worse side, at the last competitive value; its better side stays at the validity limit. A break-even found only on the better side is sweep noise: it is listed under `notBounded`, not bounded. A candidate behind the leader gets only the mass premise, and the command warns where it would overtake. Done when `concept-selection.json` and its premise records are written. Never edit a premise record by hand. To change one, select again or rerun the study.
6. **Hand off.** In the Field Lab, save the selected opportunity with **Save selected role for design**, then replay it with `node <plugin-root>/scripts/role-handoff.mjs SELECTION.json PROJECT_ROOT`. SELECTION.json is the file that button downloads, not `concept-selection.json`. [Role handoff](../../docs/season-meta-lab.md#hand-the-selected-opportunity-to-the-robot-designers) Give preliminary design the concept file, `concept-selection.json` and its premises, the faces each piece enters and leaves by, the acquisition and release poses, the aim (turret and elevation ranges and the stand-off band used), the timing, the open assumptions and the conditions that would change the role. `frc-preliminary-design` then owns the whole-robot layout. Component placement, mounting, motion and service belong there.

In the handoff, the **field prism** is the concept bot's body: frame, bumpers, stowed and maximum height and reach. The **interaction faces** are its declared input and output ports.

## Rehearse whole matches

Use [complete match rehearsals](../../docs/match-series.md) to test likely per-period behaviours for both alliances with finite piece stock, occupied robot footprints and explicit target activity. Compare the independent matches at 10× and carry observed queues and unresolved scoring conditions into the project strategy. Concept robots and robots without a concept can share one match. A robot without a concept keeps a fixed heading, a constant speed and the front intake. [Match rehearsal](../../docs/field-rehearsal.md)

In each scoring opportunity, state where the supply is, which pieces are already aboard and when loaded travel can begin. Use the loaded-batch screen for a single later transfer and preserve the assumption in the student narrative.

Use the project's [frame profile](../../docs/frame-profile.md) for the concept's outline to compare rear-corner clearance at actual headings. A concept robot that rotates occupies its circumscribed circle for that tick. Confirm close corridor estimates in the occupied rehearsal or in CAD.

Every number in a concept bot is a premise. A candidate that wins only on assumed numbers shows which of them to measure first.
